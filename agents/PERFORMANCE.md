# Performance principles

Patterns to apply from the start when writing new features, so dedicated optimization passes are not needed later.

To *measure* rather than reason — opt-in instrumentation on both the Python and browser side, plus the workflow for proving a fix with numbers — see [agents/skills/profile/SKILL.md](skills/profile/SKILL.md). `--profile` reports wall time per label plus process CPU, ffmpeg-child CPU, memory footprint and wakeups; `--profile-sample` adds CPU per thread and function and names what ran at the memory peak. `--profile-output PATH` writes the report as JSON (labels, startup marks, resources, environment, tuning settings); `tests/perf/*_bench.py` compare such runs by median and refuse mismatched fixtures or environments. Their default `smoke` tier (120 s, 1 s keyframes) is a regression gate, not a realism claim: real sessions are 1–3 h OBS recordings, so measure anything that scales with source or clip length with `--tier session`, `--scale`, or `--source` (see the profile skill).

## Count cores, not only seconds

- **A decode-bound job hides its cost in other processes.** A Screenspace scan of an hour of 1080p60 took 66 s of wall time and 520 CPU-seconds, nearly all of it in ffmpeg. The wall number alone called that fine. Read `children=` and `cores=` on the `profile | cpu` line before calling a job cheap, and gate regressions on `--fail-metric cpu` where the change is about decode or encode.
- **CPU saved is wall time under load.** Dropping non-reference frames cut one scan's CPU 46% and its wall time 15%. Two scans queued together, the default worker count, went from 107 s to 71 s each, because they stopped fighting for the same cores.
- **Check `cpu=` before parallelizing.** A label near 0% is waiting on a subprocess or a lock, and a thread pool helps. A label near 100% holds the GIL, and a thread pool only adds contention.

## Avoid redundant I/O and API calls

- **Never re-fetch what you already have.** If a function needs data that a caller already holds (e.g. `SheetContext`, parsed manifest), accept it as an optional parameter rather than re-reading from disk or network. `generate_list()` now takes `ctx: Optional[SheetContext]`; follow this pattern for any function that calls `build_sheet_context`, `get_all_values`, or reads a manifest file.
- **Read a file once, extract multiple keys.** When you need both artifacts and reels (or any two keys) from the same JSON file, use a single read/parse. See `viewer._load_manifest_both()`. Never call two separate load functions that each read the same file.
- **Google Sheets API calls are precious.** Every `sheet.get_all_values()` / `sheet.find()` / `generate_list()` is a network round-trip subject to rate limits. In server routes, always reuse the cached `_sheet_context` rather than rebuilding it. Drive's spreadsheet *listing* is likewise cached — go through `server._cached_spreadsheet_meta()` (300 s TTL, single-flight, dropped when a new account authenticates) rather than calling `google_api.get_all_spreadsheet_meta` from a route; `_spreadsheet_names_for()` re-lists once when a name isn't in the cache, and `?refresh=true` on `/api/spreadsheets/google` is the picker's manual escape hatch.

## Design for parallelism from the start

- **Batch first, iterate second.** When processing N independent items (clips, screenshots, reel segments), collect them into a list and process with `ThreadPoolExecutor`, not a sequential for-loop. Use `_resolve_clip_workers()` for the worker count and gate on `len(items) >= 2`.
- **Return results, don't mutate shared state.** Functions that run inside a thread pool must return their output rather than appending to a closure list. Assemble ordered results from the return values after the pool completes (use a pre-allocated results list indexed by future). See `process_reel_clip` returning `(segment_paths, component_dicts)` instead of appending to a shared `components` list.
- **A pool of subprocesses must divide the cores itself.** libx264 starts 1.5 frame threads per core regardless of what else runs, and each thread holds frame buffers. Four bare 4K libx264 encodes side by side held 8.7 GB on cores they were already fighting over; `-threads` at each one's share made that 5.1 GB for 1% more wall time. In the pipeline, three pooled 4K clip re-encodes went from 3.03 to 2.09 GB each for 7% more wall time (88 → 94 s), and three titlecard wraps from 2.77 to 1.90 GB. Wrap a pool in `video.encode_pool(width)` and take the cap from `video.pooled_thread_args(pixels)` or `pooled_thread_args_for(path)`. The three software encodes a pool worker runs take it: the clip re-encode, the two-pass compress and the titlecard wrap fallback. It only applies above 1440p: on small frames the same cap cost a pool of short two-pass encodes 9.5%, so measure before widening it.
- **Read a subprocess pipe on its own thread when the consumer does real work.** A full pipe blocks the writer. The Screenspace scan loop read a frame, ran the callback, then read again, so ffmpeg sat idle during every callback and wall time was decode *plus* analysis. A reader thread two frames ahead (`_ffmpeg_pipe_frames`) makes it the larger of the two: `change` on an hour of screen content went from 15.3 s to 12.0 s.
- **Streaming + parallelism can coexist.** For ndjson-streaming routes, split into two passes: (1) yield cached/skipped items immediately, (2) submit remaining work to a thread pool and yield per-future results via `as_completed()`. This preserves the per-item streaming contract while enabling parallel execution. See `/api/generate` in `server.py`.

## Pre-compute outside hot loops

- **Normalize comparison data once.** If a loop compares against a set of strings (e.g. filename matching), lowercase / normalize the set once before the loop, not inside each iteration. Sorting callbacks (`key=lambda`) are called O(n log n) times. Avoid per-call work that can be hoisted.
- **Use `DocumentFragment` for DOM batching.** When rendering lists of cards/rows, build all elements in a fragment and append once. Never append per-item inside a loop. Viewer and Screenspace already do this; apply the same pattern in any new UI list.

## Tuning knobs

Performance is already adaptive (auto-detected worker counts, lazy thumbnails, mtime caches), but a handful of `config.py` flags exist for users who want to push harder or trade fidelity for speed.

| Knob | Default | When to change it |
|---|---|---|
| `CLIP_PARALLEL_WORKERS` | `0` (auto = `min(4, cpu_count)`) | Raise on machines with fast SSDs and many cores when batch clip generation is the bottleneck. Drop to `1` to force sequential ffmpeg if disk contention is the bottleneck instead. Honored by both CLI and Studio. Each worker can hold a whole ffmpeg: a 4K software re-encode peaks near 2 GB (`child_peak=`) even with its thread cap, so on an 8 GB machine with 4K sources, lower this before anything else. |
| `SCREENSPACE_PARALLEL_WORKERS` | `2` | Raise to run more concurrent Screenspace analysis tasks. Diminishing returns past CPU core count; OpenCV is already multithreaded inside each task. |
| `WORKFLOWS_BATCH_WORKERS` | `1` | Concurrent participants per Workflows whole-study batch. Raise to 2 for light graphs (clip cutting, exports) when batch wall-clock matters. Heavy graphs (Transcribe, Detect) serialize on Whisper/ffmpeg/OCR anyway and rarely benefit; values >1 multiply peak RAM/CPU. Clamped to 4. |
| `SCREENSPACE_OCR_POOL_SIZE` | `0` (auto = `SCREENSPACE_PARALLEL_WORKERS`) | Max concurrent RapidOCR engines per recognition model. OCR (Text/Numbers tasks + calibration) borrows a distinct engine per call from a bounded pool, so this caps how many OCR calls run in parallel. Raise it to overlap more OCR work, but each engine holds its own ONNX sessions in memory so raising it multiplies OCR RAM (per-engine intra-op threads are divided by the pool size, so total CPU stays bounded). Independent of the worker count (the calibration request thread also draws from the pool). |
| `SCREENSPACE_CV_RESOLUTION_SCALE` | `1.0` | Drop below `1.0` (e.g. `0.5`) to scan large footage faster at the cost of detection fidelity. Raise above `1.0` only when the source is noisy/compressed and detectors miss small artifacts. |
| `SCREENSPACE_FAST_SCAN_SKIP_NONKEY` | `True` | Fast scans decode only keyframes on H.264/HEVC, giving GOP-sized (often 30–250×) decode savings, the dominant cost across all Screenspace tools (`select=` runs post-decode, so without this ffmpeg fully decodes ~every frame just to drop most). Enabled per-video only when the probed worst-case keyframe gap (`video.probe_max_keyframe_gap`) is ≤ the sampling interval; the sample grid is then tightened by that gap so coverage is never coarser than the interval. Set `False` to never decode keyframes only. Long/variable-GOP sources fall back to reference-only or full decode; this knob never affects the precise (non-fast) scan path. Tuning: `SCREENSPACE_KEYFRAME_PROBE_SECONDS` (probe window) and `SCREENSPACE_KEYFRAME_SKIP_MARGIN` (how sparse keyframes may be, as a fraction of the interval, before backing off). |
| `SCREENSPACE_REFERENCE_FRAMES_ONLY` | `True` | Scans decode only the frames other frames are predicted from (`-skip_frame noref`), on H.264/HEVC, in **every** scan mode. The frames that remain are bit-identical to a full decode; each sample is the first reference frame in its interval, so it lands at most one reference gap after the grid point (83 ms on a 60 fps recording with four B-frames). Engages per video only when the scan spans ≥ 120 s, the probed gap (`video.probe_max_reference_gap`, first 5 s, ~0.3 s once per file) shows droppable frames, and the gap is ≤ `SCREENSPACE_REFERENCE_GAP_MARGIN` (0.15) of the interval; keyframe-only decode wins when both qualify. Measured on a 58-min 1080p60 recording: **66 s wall / 520 CPU-s → 56 s / 280 CPU-s** per tool, and 107 s → 71 s each for two scans at once, with 1815 vs 1816 change events. Set `False` to decode every frame; streams without B-frames are unaffected either way. |
| `FFMPEG_VIDEO_ENCODER` | `"auto"` | H.264 encoder for the re-encode paths (reel filter_complex concat, the concat re-encode fallback, clip re-encode, timelapse mp4, Composer burn-in). `auto` uses `h264_videotoolbox` when `ffmpeg -encoders` lists it and it hasn't failed this session. Measured on a 1080p/60 s re-encode: **48.4 s wall / 524 s CPU (libx264) → 12.5 s / 20.6 s (VideoToolbox)**, at the cost of larger files for the same visual quality (VideoToolbox has no CRF; `video.video_encoder_args` maps a CRF onto `-q:v`). The win needs a real workload — on a short 720p clip the filter graph and encoder setup dominate and VideoToolbox came out *slower*. One runtime failure flips a session-sticky flag (`video.note_hw_encode_failure`) and everything after it uses libx264, so a broken media engine costs one wasted encode, not one per clip. Set `libx264` to always encode in software (argv is then byte-identical to pre-hardware clipgen). Two paths are deliberately **excluded**: titlecard/endcard generation (cards must parameter-match the clip body they wrap) and `compress_to_size` (bitrate targeting — VideoToolbox has no `-pass` and overshot a 105 kbps target by 2.3×, so the attempt would be discarded and the two-pass paid for anyway). |
| `GALLERY_BUNDLE_ENABLED` | `False` | Set to `True` to inline gallery images as base64, producing a single-file HTML viewer. **Do not enable for large galleries.** The HTML balloons to hundreds of MB and browsers choke. |
| `TITLECARD_ENCODE_PRESET` / `TITLECARD_ENCODE_CRF` | `veryfast` / `20` | x264 preset + CRF for title/endcard generation and the card wrap. The wrap now stream-copies the clip body via the concat demuxer when the body is copy-safe (h264 / yuv420p, with cards rebuilt to match the body's fps + aac audio), re-encoding only the two ~2 s cards, so the preset dominates titlecard time only on the fallback re-encode path (non-h264/exotic bodies, or a failed copy concat). `veryfast` is several times faster than libx264's `medium` default. Drop to `superfast`/`ultrafast` for more speed (larger files), or lower the CRF for higher quality. |
| `TRANSCRIBE_DEVICE` | `"auto"` | Compute device for Whisper. `auto` means CPU in the desktop bundle, which ships no CUDA runtime, and passes through to CTranslate2 from a source checkout. Set `cuda` only with a matching cuBLAS/cuDNN installed — CTranslate2 brings its own CUDA detection and does *not* consult torch, so an unbacked `cuda` fails at the first inference rather than at load. |
| `TRANSCRIBE_CPU_THREADS` | `0` (auto = `os.cpu_count()`) | CTranslate2 CPU threads for Whisper. CT2's own default under-uses many-core CPUs; auto resolves to all cores. No effect on output text. Pure speed. |
| `TRANSCRIBE_BEAM_SIZE` | `2` | Whisper beam-search width. `1` (greedy) is ~2–3× faster decode for a small accuracy cost on disfluent/accented speech; raise toward `5` for marginally better accuracy at proportional cost. |
| `TRANSCRIBE_VAD_FILTER` (+ `_THRESHOLD` / `_SPEECH_PAD_MS` / `_MIN_SILENCE_MS`) | `True` (0.2 / 400 / 2000) | Silero VAD skips long silence, the big win on mostly-quiet UX recordings. Defaults are recall-safe (permissive threshold + boundary padding). If real words drop, lower the threshold or raise the pad rather than disabling VAD. |
| `TRANSCRIBE_WORD_TIMESTAMPS` | `True` | Per-word DTW alignment: tightens segment boundaries to the spoken words (removing the VAD pad slack) and powers the word-level playback highlight, at ~10–30% added decode time (worse on larger models). Disable for bulk transcription runs where per-word timing doesn't matter. |
| `TRANSCRIBE_EDGE_SNAP` | `True` | RMS-envelope snap of segment edges to measured speech in the already-decoded audio (trims Whisper's silence overshoot). One vectorized pass per file, ~100 ms per audio-hour — effectively free; only disable to debug boundary placement. |
