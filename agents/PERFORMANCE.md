# Performance principles

Patterns to apply from the start when writing new features, so dedicated optimization passes are not needed later.

## Avoid redundant I/O and API calls

- **Never re-fetch what you already have.** If a function needs data that a caller already holds (e.g. `SheetContext`, parsed manifest), accept it as an optional parameter rather than re-reading from disk or network. `generate_list()` now takes `ctx: Optional[SheetContext]`; follow this pattern for any function that calls `build_sheet_context`, `get_all_values`, or reads a manifest file.
- **Read a file once, extract multiple keys.** When you need both artifacts and reels (or any two keys) from the same JSON file, use a single read/parse. See `viewer._load_manifest_both()`. Never call two separate load functions that each read the same file.
- **Google Sheets API calls are precious.** Every `sheet.get_all_values()` / `sheet.find()` / `generate_list()` is a network round-trip subject to rate limits. In server routes, always reuse the cached `_sheet_context` rather than rebuilding it. Drive's spreadsheet *listing* is likewise cached — go through `server._cached_spreadsheet_meta()` (300 s TTL, single-flight, dropped when a new account authenticates) rather than calling `google_api.get_all_spreadsheet_meta` from a route; `_spreadsheet_names_for()` re-lists once when a name isn't in the cache, and `?refresh=true` on `/api/spreadsheets/google` is the picker's manual escape hatch.

## Design for parallelism from the start

- **Batch first, iterate second.** When processing N independent items (clips, screenshots, reel segments), collect them into a list and process with `ThreadPoolExecutor`, not a sequential for-loop. Use `_resolve_clip_workers()` for the worker count and gate on `len(items) >= 2`.
- **Return results, don't mutate shared state.** Functions that run inside a thread pool must return their output rather than appending to a closure list. Assemble ordered results from the return values after the pool completes (use a pre-allocated results list indexed by future). See `process_reel_clip` returning `(segment_paths, component_dicts)` instead of appending to a shared `components` list.
- **Streaming + parallelism can coexist.** For ndjson-streaming routes, split into two passes: (1) yield cached/skipped items immediately, (2) submit remaining work to a thread pool and yield per-future results via `as_completed()`. This preserves the per-item streaming contract while enabling parallel execution. See `/api/generate` in `server.py`.

## Pre-compute outside hot loops

- **Normalize comparison data once.** If a loop compares against a set of strings (e.g. filename matching), lowercase / normalize the set once before the loop, not inside each iteration. Sorting callbacks (`key=lambda`) are called O(n log n) times. Avoid per-call work that can be hoisted.
- **Use `DocumentFragment` for DOM batching.** When rendering lists of cards/rows, build all elements in a fragment and append once. Never append per-item inside a loop. Viewer and Screenspace already do this; apply the same pattern in any new UI list.

## Tuning knobs

Performance is already adaptive (auto-detected worker counts, lazy thumbnails, mtime caches), but a handful of `config.py` flags exist for users who want to push harder or trade fidelity for speed.

| Knob | Default | When to change it |
|---|---|---|
| `CLIP_PARALLEL_WORKERS` | `0` (auto = `min(4, cpu_count)`) | Raise on machines with fast SSDs and many cores when batch clip generation is the bottleneck. Drop to `1` to force sequential ffmpeg if disk contention is the bottleneck instead. Honored by both CLI and Studio. |
| `SCREENSPACE_PARALLEL_WORKERS` | `2` | Raise to run more concurrent Screenspace analysis tasks. Diminishing returns past CPU core count; OpenCV is already multithreaded inside each task. |
| `WORKFLOWS_BATCH_WORKERS` | `1` | Concurrent participants per Workflows whole-study batch. Raise to 2 for light graphs (clip cutting, exports) when batch wall-clock matters. Heavy graphs (Transcribe, Detect) serialize on Whisper/ffmpeg/OCR anyway and rarely benefit; values >1 multiply peak RAM/CPU. Clamped to 4. |
| `SCREENSPACE_OCR_POOL_SIZE` | `0` (auto = `SCREENSPACE_PARALLEL_WORKERS`) | Max concurrent EasyOCR Readers per language set. OCR (Text/Numbers tasks + calibration) borrows a distinct Reader per call from a bounded pool, so this caps how many OCR calls run in parallel. Raise it to overlap more OCR work, but each Reader holds its own model copy in memory so raising it multiplies OCR RAM/VRAM. Independent of the worker count (the calibration request thread also draws from the pool). |
| `SCREENSPACE_OCR_GPU` | `True` | EasyOCR device selection. `True` uses CUDA when available (else CPU, EasyOCR's default); `False` forces CPU; a device string (`"cuda:0"`, `"mps"`) targets a specific device. On GPU, a larger `SCREENSPACE_OCR_POOL_SIZE` multiplies VRAM. |
| `SCREENSPACE_CV_RESOLUTION_SCALE` | `1.0` | Drop below `1.0` (e.g. `0.5`) to scan large footage faster at the cost of detection fidelity. Raise above `1.0` only when the source is noisy/compressed and detectors miss small artifacts. |
| `SCREENSPACE_FAST_SCAN_SKIP_NONKEY` | `True` | Fast scans decode only keyframes on H.264/HEVC, giving GOP-sized (often 30–250×) decode savings, the dominant cost across all Screenspace tools (`select=` runs post-decode, so without this ffmpeg fully decodes ~every frame just to drop most). Enabled per-video only when the probed worst-case keyframe gap (`video.probe_max_keyframe_gap`) is ≤ the sampling interval; the sample grid is then tightened by that gap so coverage is never coarser than the interval. Set `False` to always full-decode. Long/variable-GOP sources auto-fall back to full decode; the precise (non-fast) scan path is never affected. Tuning: `SCREENSPACE_KEYFRAME_PROBE_SECONDS` (probe window) and `SCREENSPACE_KEYFRAME_SKIP_MARGIN` (how sparse keyframes may be, as a fraction of the interval, before backing off). |
| `FFMPEG_VIDEO_ENCODER` | `"auto"` | H.264 encoder for the re-encode paths (reel filter_complex concat, the concat re-encode fallback, clip re-encode, timelapse mp4, Composer burn-in). `auto` uses `h264_videotoolbox` when `ffmpeg -encoders` lists it and it hasn't failed this session. Measured on a 1080p/60 s re-encode: **48.4 s wall / 524 s CPU (libx264) → 12.5 s / 20.6 s (VideoToolbox)**, at the cost of larger files for the same visual quality (VideoToolbox has no CRF; `video.video_encoder_args` maps a CRF onto `-q:v`). The win needs a real workload — on a short 720p clip the filter graph and encoder setup dominate and VideoToolbox came out *slower*. One runtime failure flips a session-sticky flag (`video.note_hw_encode_failure`) and everything after it uses libx264, so a broken media engine costs one wasted encode, not one per clip. Set `libx264` to always encode in software (argv is then byte-identical to pre-hardware clipgen). Two paths are deliberately **excluded**: titlecard/endcard generation (cards must parameter-match the clip body they wrap) and `compress_to_size` (bitrate targeting — VideoToolbox has no `-pass` and overshot a 105 kbps target by 2.3×, so the attempt would be discarded and the two-pass paid for anyway). |
| `GALLERY_BUNDLE_ENABLED` | `False` | Set to `True` to inline gallery images as base64, producing a single-file HTML viewer. **Do not enable for large galleries.** The HTML balloons to hundreds of MB and browsers choke. |
| `TITLECARD_ENCODE_PRESET` / `TITLECARD_ENCODE_CRF` | `veryfast` / `20` | x264 preset + CRF for title/endcard generation and the card wrap. The wrap now stream-copies the clip body via the concat demuxer when the body is copy-safe (h264 / yuv420p, with cards rebuilt to match the body's fps + aac audio), re-encoding only the two ~2 s cards, so the preset dominates titlecard time only on the fallback re-encode path (non-h264/exotic bodies, or a failed copy concat). `veryfast` is several times faster than libx264's `medium` default. Drop to `superfast`/`ultrafast` for more speed (larger files), or lower the CRF for higher quality. |
| `TRANSCRIBE_CPU_THREADS` | `0` (auto = `os.cpu_count()`) | CTranslate2 CPU threads for Whisper. CT2's own default under-uses many-core CPUs; auto resolves to all cores. No effect on output text. Pure speed. |
| `TRANSCRIBE_BEAM_SIZE` | `2` | Whisper beam-search width. `1` (greedy) is ~2–3× faster decode for a small accuracy cost on disfluent/accented speech; raise toward `5` for marginally better accuracy at proportional cost. |
| `TRANSCRIBE_VAD_FILTER` (+ `_THRESHOLD` / `_SPEECH_PAD_MS` / `_MIN_SILENCE_MS`) | `True` (0.2 / 400 / 2000) | Silero VAD skips long silence, the big win on mostly-quiet UX recordings. Defaults are recall-safe (permissive threshold + boundary padding). If real words drop, lower the threshold or raise the pad rather than disabling VAD. |
